---
title: Verify application auth end to end
description: Prove every built-in application verifier works against a running proxy and, where required, a real device.
---

omni-model ships several user and application-verification methods. This page shows how to prove
each one actually accepts a **real** credential (and rejects a forged one) against a **running**
proxy.

The verification splits in two, because two of the four can only be produced by a physical device:

| Method | Verifier | How it's verified | Device? |
| --- | --- | --- | --- |
| Firebase Auth | `firebase-auth` | Automated e2e mints a real ID token via Google's Identity Toolkit | No |
| Firebase App Check | `firebase-app-check` | Automated e2e exchanges a registered **debug token** for a real App Check token | No |
| Apple App Attest | `apple-app-attest` | The example iOS app runs the challenge → attest → assert flow on device | **Yes** |
| Apple DeviceCheck | `apple-device-check` | The example iOS app generates a DeviceCheck token on device | **Yes** |
| Cloudflare Turnstile | `cloudflare-turnstile` | A browser widget creates a fresh token; the proxy calls Siteverify | No |
| reCAPTCHA Enterprise | `recaptcha-enterprise` | A web or mobile SDK token is assessed by Google Cloud | Mobile only |
| Google Play Integrity | `google-play-integrity` | The Android app binds a Standard API verdict to the exact HTTP request | **Yes** |

The offline `application-verification.e2e.test.ts` and `user-authentication.e2e.test.ts` suites
also start real Node servers and drive Turnstile, reCAPTCHA Enterprise, Play Integrity, Clerk, and
Cognito through deterministic identity/vendor endpoints. They verify the complete header → auth
layer → model-upstream path without credentials or network access:

```sh
pnpm test:e2e
```

Use the real-service checks below before production; the deterministic suite proves integration
wiring and failure boundaries, while vendor credentials and console enrollment remain
deployment-specific.

<Note>
App Attest and DeviceCheck use the Secure Enclave — `DCAppAttestService`/`DCDevice` report
`isSupported == false` on the simulator. There is no REST shortcut; a real device is required.
</Note>

## The configuration

Firebase Auth identifies the user on every request. App Check, App Attest, and
DeviceCheck are application-verification alternatives, so `appAuth.mode: any`
accepts the proof the current platform can produce:

```sh
export OMNI_SECURITY_USER_AUTH_JSON='{
  "type":"firebase-auth",
  "projectId":"${FIREBASE_PROJECT_ID}"
}'
export OMNI_SECURITY_APP_AUTH_JSON='{
  "mode":"any",
  "providers":[
    {"type":"firebase-app-check","projectNumber":"${FIREBASE_PROJECT_NUMBER}"},
    {"type":"apple-app-attest","teamId":"${APPLE_TEAM_ID}","bundleId":"${APPLE_BUNDLE_ID}","environment":"development"},
    {"type":"apple-device-check","teamId":"${APPLE_TEAM_ID}","keyId":"${APPLE_DEVICECHECK_KEY_ID}","privateKey":"${APPLE_DEVICECHECK_KEY}","development":true}
  ]
}'
```

<Warning>
Two settings must match your **build**, or a genuine token is rejected:
- **App Attest `environment`** — a debug build run from Xcode produces *development*-environment
  attestations; `environment: development` (the default here) accepts them. A TestFlight/App Store
  build produces *production* — flip both `environment` and DeviceCheck's `development` to match.
- **Use `postgres` storage when running more than one replica.** App Attest registers a key on one
  request and verifies an assertion on another; those can land on different instances, so the
  registered key must live in shared storage rather than in a single process's memory.
</Warning>

<Note>
**Upstream region blocks are not auth failures.** Some upstreams geo-restrict models — OpenRouter
returns `403 "This model is not available in your region"` for requests egressing from certain
regions, for example. When that happens the credential was still **accepted** (the request passed
auth and reached the upstream); the on-device screen shows this as an amber **AUTH OK** (not a red
FAIL). Pick a model your upstream serves in your region, or use a direct provider
(OpenAI/Anthropic/Gemini), to get a green PASS.
</Note>

## Prerequisites

- The app's **`GoogleService-Info.plist`** (its `PROJECT_ID`, `GCM_SENDER_ID`, `BUNDLE_ID`).
- Your **Apple Team ID** (10 chars) — for both Apple verifiers.
- A **DeviceCheck key**: the `.p8` file + its **Key ID**, from App Store Connect → Users and
  Access → Integrations → Keys → DeviceCheck.
- For the automated App Check test: a registered **App Check debug token** (Firebase console →
  App Check → your app → Manage debug tokens) and the app's `GOOGLE_APP_ID` + Web `API_KEY`.

## Part 1 — automated Firebase Auth + App Check

The live E2E suite stands up a real proxy and checks each Firebase credential
against the real project while keeping its model upstream local. Run it from
[`e2e/`](https://github.com/tiepvuvan/omni-model/tree/main/e2e):

```sh
export FIREBASE_API_KEY=...          # plist API_KEY
export FIREBASE_PROJECT_ID=...       # plist PROJECT_ID
export FIREBASE_PROJECT_NUMBER=...   # plist GCM_SENDER_ID
export FIREBASE_APP_ID=...           # plist GOOGLE_APP_ID          (App Check)
export GOOGLE_APPLICATION_CREDENTIALS=/secure/service-account.json
export FIREBASE_APPCHECK_DEBUG_TOKEN_FILE=/secure/app-check-debug-token
export OMNI_E2E_REQUIRE_FIREBASE=auth,app-check,combined
pnpm test:e2e -- e2e/live-providers/firebase.e2e.test.ts
```

It asserts: missing or forged Firebase ID token → **401**, genuine Firebase ID
token → **200**, bogus App Check token → **401**, genuine App Check token →
**200**, and both credentials are required by the combined configuration. The
service-account path lets the suite create and delete a disposable user without
enabling Anonymous sign-in. Add `replay-protection` to the strict gate and set
`FIREBASE_APPCHECK_TEST_CONSUME=true` to verify limited-use-token consumption.

The companion Apple suite additionally proves the DeviceCheck signing key and
the App Attest challenge route, which need no device-generated proof.

## Part 2 — on device (all four), against a deployed proxy

A phone can't reach your Mac's `localhost`, so deploy the proxy first (or expose it with a tunnel).

<Steps>
<Step title="Deploy the proxy">
Deploy the [container](/installation/docker) with this environment configuration and set the
secrets. The multi-line `.p8` is one environment variable — keep the newlines intact:

```sh
export APPLE_DEVICECHECK_KEY="$(cat AuthKey_XXXX.p8)"
# ...plus OMNI_SECURITY_JSON from above, OMNI_STORAGE_TYPE=postgres,
#         OMNI_STORAGE_POSTGRES_URL, OMNI_ROUTING_JSON, OMNI_ROUTING_JSON,
#         FIREBASE_PROJECT_ID, FIREBASE_PROJECT_NUMBER, APPLE_TEAM_ID,
#         APPLE_BUNDLE_ID, APPLE_DEVICECHECK_KEY_ID, OPENROUTER_API_KEY.
```

Note the public URL — you'll paste it into the app.
</Step>

<Step title="Configure the example app">
In [`examples/ios-app`](https://github.com/tiepvuvan/omni-model/tree/main/examples/ios-app):
- Replace `Resources/GoogleService-Info.plist` with your project's (don't commit it).
- Generate the project with your identifiers (kept out of the repo):

```sh
cd examples/ios-app
TUIST_OMNI_BUNDLE_ID=co.unstatic.polyplan TUIST_OMNI_DEVELOPMENT_TEAM=ABCDE12345 tuist generate
```

The bundle id must match `apple-app-attest.bundleId` and the Firebase-registered app; the Team must
own the DeviceCheck key. The App Attest entitlement (`appattest-environment: development`) is already
wired in `Project.swift`.
</Step>

<Step title="Run on a real device">
Open the workspace, select your device, and run. The **Auth verification** screen has a URL field for
the proxy. Paste your URL, then tap **Run all** — each method reports **PASS** (the proxy accepted the
credential and completed a chat) or **FAIL** (with the reason).
</Step>
</Steps>

Under the hood each row refreshes an `OmniAuthBox` from one `OmniAuthProvider`
(`FirebaseIDTokenAuth` / `FirebaseAppCheckAuth` / `DeviceCheckAuth` / `AppAttestAuth`) and sends a
real request through the MacPaw/OpenAI client — the same [Swift integration](/integrations/swift)
your app uses.
