---
title: Firebase App Check
description: Verify that requests to the self-hosted proxy come from an authentic instance of your app.
---

Firebase App Check attests that a request originates from an authentic,
untampered instance of your app rather than an automated script or a stolen key.
The `firebase-app-check` verifier validates the App Check token that the
Firebase SDK attaches, on the **self-hosted HTTP proxy**.

App Check tokens carry no user identity — they attest the app *instance*.
`user.providers` includes `firebase-app-check`, and its verified token claims
are available under `user.claims.<verifier-name>`. Configure the required
`security.userAuth` separately; use [`firebase-auth`](/security/custom-jwt)
when both credentials should come from Firebase.

<Note>
**You do not need Firebase Hosting or Functions to use this.** The verifier only
validates App Check tokens against Google's public keys, so it works from any
container. Only `consume: true` (replay protection) additionally needs Firebase
Admin credentials — see below.
</Note>

## Configuration

```sh
export OMNI_SECURITY_USER_AUTH_JSON='{
  "type":"firebase-auth",
  "projectId":"my-app-12345"
}'
export OMNI_SECURITY_APP_AUTH_JSON='{
  "mode":"all",
  "providers":[{
    "type":"firebase-app-check",
    "projectNumber":"1234567890",
    "appIds":["1:1234567890:ios:abcdef123456"]
  }]
}'
```

<ParamField path="projectNumber" type="string">
The **numeric** Firebase project number — not the project id. The verifier pins
the issuer to `https://firebaseappcheck.googleapis.com/<projectNumber>` and the
audience to `projects/<projectNumber>`. Required: set it here, or as
`OMNI_GCP_PROJECT_NUMBER` in the environment. It is the `GCM_SENDER_ID` in your
app's `GoogleService-Info.plist` / `google-services.json`.
</ParamField>
<ParamField path="appIds" type="string[]">
Optional allowlist of Firebase app ids, matched against the token `sub`. When
omitted, any app in the project is accepted.
</ParamField>
<ParamField path="header" type="string" default="x-firebase-appcheck">
Header carrying the raw App Check token (no `Bearer` prefix).
</ParamField>
<ParamField path="consume" type="boolean" default="false">
Enable Firebase's limited-use token replay protection. The proxy consumes each token using the
Firebase Admin SDK; a second use returns `401`. Only enable this after every client obtains a new
limited-use token for every proxy request. This is the one App Check feature that needs Firebase
Admin credentials in the container — see below.
</ParamField>
<ParamField path="clockToleranceSeconds" type="integer" default="60">
Allowed clock skew, in seconds.
</ParamField>

Tokens are RS256 JWTs verified against Google's App Check JWKS
(`https://firebaseappcheck.googleapis.com/v1/jwks`). A token with no subject, or
a subject outside the `appIds` allowlist, is rejected with a token-free reason.

## Replay protection with limited-use tokens

Session App Check tokens are intentionally reusable until their expiry. For low-volume, costly, or
security-sensitive proxy operations, set `consume: true` (or the named environment variable) to
make Firebase consume each token after its local signature, project, and app-id checks pass:

```sh
export OMNI_SECURITY_FIREBASE_APPCHECK_CONSUME=true
```

This adds a Firebase verification round trip to every request and fails closed if it cannot be
completed. Give the container a service account credential (mount the key and set
`GOOGLE_APPLICATION_CREDENTIALS`, plus `FIREBASE_PROJECT_ID`), and grant that account the Firebase
App Check Token Verifier role:

```sh
gcloud projects add-iam-policy-binding "$PROJECT_ID" \
  --member="serviceAccount:${RUNTIME_SA}" \
  --role="roles/firebaseappcheck.tokenVerifier"
```

Clients must request a **new limited-use token per request**; an ordinary cached App Check session
token will succeed once and then be rejected as a replay. For example, on Apple platforms use
`try await AppCheck.appCheck().limitedUseToken()` instead of `token(forcingRefresh:)` before
placing the result in `X-Firebase-AppCheck`. Firebase documents the latency and attestation-quota
tradeoff for this beta protection in its
[custom-backend replay-protection guide](https://firebase.google.com/docs/app-check/custom-resource-backend).

<Note>
**Supplying the project number from the environment.** If you would rather keep
it out of the config document, set `OMNI_GCP_PROJECT_NUMBER` and omit the field:

```sh
export OMNI_GCP_PROJECT_NUMBER=1234567890
export OMNI_SECURITY_APP_AUTH_JSON='{"providers":[{"type":"firebase-app-check"}]}'
```

Explicit `projectNumber` always wins, which is how cross-project deployments
work. Either way it must resolve at startup — a missing project number is a
startup failure, not a per-request one. Note that this does not enroll an app in
Firebase App Check or configure an attestation provider; complete those steps in
the Firebase console first.
</Note>

## Sending the token

Fetch a token with the Firebase App Check SDK on the client, then send it in the
`X-Firebase-AppCheck` header on every request. Unlike the JWT verifiers, this
header carries the **raw token** with no `Bearer` scheme.

```bash
curl https://your-proxy.example.com/v1/chat/completions \
  -H "X-Firebase-AppCheck: $APP_CHECK_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"model":"gpt-4o-mini","messages":[{"role":"user","content":"hi"}]}'
```

## Requiring App Check and a user

The user layer is always required. Add App Check under `appAuth` to require an
authentic app instance on that same request:

```sh
export OMNI_SECURITY_USER_AUTH_JSON='{
  "type":"firebase-auth",
  "projectId":"${GOOGLE_CLOUD_PROJECT}"
}'
export OMNI_SECURITY_APP_AUTH_JSON='{
  "mode":"all",
  "providers":[
    {"type":"firebase-app-check","projectNumber":"${FIREBASE_PROJECT_NUMBER}"}
  ]
}'
```

If either credential is absent or invalid, the request is rejected before
routing. The merged identity carries `firebase-app-check` and `firebase-auth`
in `user.providers`, plus `user.id` from Firebase Auth, into
[routing and rate-limit rules](/model-routing/routing).
Set `projectNumber` (App Check) and `projectId` (Firebase Auth) explicitly —
they are different values from the same Firebase project.

## Verify against a real Firebase project

The live E2E suite creates a disposable Firebase user, verifies its real ID
token, exchanges a registered debug secret for a real App Check token, and
proves both layers are required together. Optional replay coverage requests a
limited-use token, consumes it through Firebase Admin, and rejects its reuse.
The model upstream is deterministic, so no model provider key or token cost is
involved.

See the [E2E Firebase setup](https://github.com/tiepvuvan/omni-model/blob/main/e2e/README.md#live-firebase-authentication-and-app-check)
for the secure debug-token file, strict CI gate, and commands.
