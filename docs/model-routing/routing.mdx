---
title: Model routing
description: How omni-model selects a named upstream, optional fallback, and model for each request.
---

Routing turns an incoming request into a decision: **which named provider, with which fallback, as
which model**. It lets you expose stable client-facing names — a `"smart"` alias, a `"claude-*"` family —
and map them to concrete upstreams by user tier, request shape, headers or time, without shipping any
of that logic in your app.

The rules live in the `routing` block and are evaluated by
`packages/core/src/routing/router.ts`.

Every `when` field is a [CEL expression](/model-routing/expressions). Read that page first if you
have not — the missing-key gotcha bites here too.

## One list, first match wins

```json
{
  "providers": {
    "anthropic-primary": {
      "type": "anthropic",
      "apiKey": "${ANTHROPIC_API_KEY}"
    },
    "openai-backup": {
      "type": "openai",
      "apiKey": "${OPENAI_API_KEY}"
    }
  },
  "routing": {
    "rules": [
      {
        "id": "pro-users",
        "when": "request.model == \"smart\" && has(user.claims.tier) && user.claims.tier == \"pro\"",
        "target": {
          "provider": "anthropic-primary",
          "fallbackProvider": "openai-backup",
          "model": "claude-sonnet-5"
        }
      },
      {
        "id": "everyone-else",
        "when": "true",
        "target": { "provider": "openai-backup", "model": "gpt-4o-mini" }
      }
    ]
  }
}
```

Rules are evaluated top to bottom. The first one whose condition is exactly boolean `true` wins, and
nothing after it runs.

There is no separate default stage: **a catch-all is a last rule with `when: "true"`.** If no rule
matches, the request is a 404 `model_not_found` — which is what you want for a name nothing is
configured to serve.

## Configure providers once

The top-level `providers` map owns endpoints and credentials. Each key is a stable provider ID.
Rules only select that ID, an optional fallback ID, and a model. This keeps credentials centralized,
lets several rules reuse one account, and lets you configure several accounts of the same type.

```json
{
  "providers": {
    "groq-free": {
      "type": "openai-compatible",
      "baseUrl": "https://api.groq.com/openai/v1",
      "apiKey": "${GROQ_API_KEY}"
    }
  },
  "routing": {
    "rules": [{
      "id": "free-tier",
      "when": "!has(user.claims.tier)",
      "target": {
        "provider": "groq-free",
        "model": "llama-3.3-70b-versatile"
      }
    }]
  }
}
```

Saving a rule that references an unknown provider is rejected before it can become active. Removing
a provider is likewise rejected while any primary or fallback target still points to it.

`model` is the upstream name to forward as. **Omit it to pass the client's model through
unchanged** — which is what a rule dispatching a family of real model names wants:

```json
{
  "id": "anthropic-family",
  "when": "request.model.startsWith(\"claude-\")",
  "target": { "provider": "anthropic-primary" }
}
```

Set it when you are inventing an alias; leave it off when the client already knows the real name.

DeepSeek is a first-class provider, so its public API root is filled in automatically:

```json
{
  "providers": {
    "deepseek": { "type": "deepseek", "apiKey": "${DEEPSEEK_API_KEY}" }
  },
  "routing": {
    "rules": [{
      "id": "deepseek",
      "when": "request.model.startsWith(\"deepseek-\")",
      "target": { "provider": "deepseek" }
    }]
  }
}
```

The model remains a normal routing value. Current DeepSeek model names such as
`deepseek-v4-flash` pass through unchanged, or a rule can map a client-facing alias to one with
`target.model`.

See the [configuration reference](/reference/configuration#target-fields) for each provider type's
fields, or ask a running deployment: `GET /admin/api/meta` publishes them as JSON Schema.

## Fallback providers

Set `fallbackProvider` when a rule should retry one other provider after the primary returns or
throws an upstream error:

```json
{
  "provider": "openai-primary",
  "fallbackProvider": "openai-backup",
  "model": "gpt-4o-mini"
}
```

The fallback must be a different configured provider. It is not load balancing and it is not tried
after a successful response. Request logs record the provider that actually answered.

## What clients may ask for

`allowedModels` is the client-facing catalogue. A request for anything else is a 404 **before any
rule runs**, and `GET /v1/models` lists exactly these names.

```json
{ "routing": { "allowedModels": ["smart", "fast"], "rules": [] } }
```

Leave it empty and every name is eligible for routing. `/v1/models` then falls back to the distinct
models the rules forward to, because a rule matching a pattern cannot be enumerated.

Client-facing names never have to match upstream names — that is what a target's `model` is for. A
write key can narrow the list further; see [write keys](/reference/write-keys).

## Two silent failures, and how to see them

CEL has two behaviours that make a broken rule invisible rather than loud:

- Reading a **missing map key throws**. An unguarded `user.claims.tier == "pro"` throws for any user
  without that claim, and the router treats a throw as "no match".
- **Only a literal `true` matches.** A truthy string or number does not.

Both are correct for serving traffic — one bad expression must not 500 every request — and both mean
the rule simply never fires. `POST /admin/api/routing/simulate` is how you see it:

```sh
curl -b cookies.txt -X POST https://your-proxy/admin/api/routing/simulate \
  -H 'content-type: application/json' \
  -d '{"model":"smart","claims":{"tier":"pro"}}'
```

```json
{
  "matched": true,
  "route": "everyone-else",
  "rules": [{ "rule": "pro-users", "outcome": "error", "error": "no such key: tier" }],
  "warnings": ["rule \"pro-users\" throws for this request and can therefore never match: …"]
}
```

Guard optional fields with `has()`:

```json
{ "when": "has(user.claims.tier) && user.claims.tier == \"pro\"" }
```

## Order is meaning

Adding a rule to a list that already ends in a catch-all appends it **after** that
catch-all — where first-match-wins makes it dead on arrival. The proxy keeps
answering normally from the earlier rule, so nothing about a request reveals it.

Saving through the admin API says so:

```json
{
  "revision": 3,
  "warnings": [
    "rule \"premium\" can never match: \"default\" earlier in the list matches everything (when: \"true\"). Move \"premium\" above it — rules are evaluated in order and the first match wins."
  ]
}
```

The proxy also logs it at boot. Keep the catch-all last, and put specific rules above
it. Reordering is `PUT /routing` with the whole list — the only request that can
express a new order.

## Rule fields

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `when` | string | yes | CEL expression. Only a literal `true` counts as a match. |
| `target` | object | yes | Where a match goes: `provider`, optional `fallbackProvider`, and optional `model`. |
| `id` | string | no | Stable identity, used by request logs and the admin API. Defaults to the rule's position — set it explicitly if anything edits rules programmatically, since a positional id changes meaning when rules are reordered. |
| `name` | string | no | Human label, shown as the route name in request logs. Defaults to `id`. |

| `routing` field | Type | Required | Description |
| --- | --- | --- | --- |
| `allowedModels` | string array | no (default `[]`) | Client-facing catalogue. Empty means no restriction. |
| `rules` | array | no (default `[]`) | Evaluated in order; first match wins. |

## What ends up in the logs

Every request records the rule that served it and the named provider that actually answered, so
`GET /admin/api/logs` answers "where did this go and what did it cost" per request. See
[logging](/reference/logging).
