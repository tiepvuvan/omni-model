---
title: Publishable keys
description: Generate, attribute, restrict, and revoke the applications calling your proxy.
---

A publishable key answers **which application is calling**. That is separate from the
[user authentication method](/security/custom-jwt), which answers *who is using that application*.
Every protected request can carry both credentials.

## Generate and manage keys

Open **Public API Keys** in the dashboard to:

- generate a key with a recognizable reference name;
- see its expiration, total token usage, last model, and last request time;
- revoke it without deleting its request history.

The plaintext is shown exactly once after generation. Copy it before closing the dialog. Only its
SHA-256 hash is stored, so an operator cannot retrieve it later and a database dump cannot be used
as a credential.

You can perform the same actions through the [admin API](/reference/admin-api):

```sh
curl -X POST https://your-proxy/admin/api/write-keys \
  -H "content-type: application/json" \
  -b "$ADMIN_COOKIE" \
  -d '{"name":"iOS production"}'
```

Revocation keeps the row so past request logs and usage remain attributable.

<Note>
  Each replica caches key lookups in memory briefly. Revocation takes effect immediately on the
  instance that performed it and within the key-cache TTL on other replicas.
</Note>

## Send a key

Publishable keys use the standard OpenAI credential transport:

```http
Authorization: Bearer omk_gH3k…
```

This means an OpenAI SDK can use the key directly as its `apiKey`:

```ts
import OpenAI from "openai";

const client = new OpenAI({
  apiKey: "omk_gH3k…",
  baseURL: "https://your-proxy/v1",
  defaultHeaders: {
    "X-Firebase-ID-Token": userIdToken,
  },
});
```

`Authorization` belongs to the publishable key. End-user credentials use dedicated headers so both
layers can be sent on the same request:

| User authentication method | Default header | Value |
| --- | --- | --- |
| Firebase Auth | `X-Firebase-ID-Token` | Raw Firebase ID token |
| Clerk | `X-Clerk-Session-Token` | Raw Clerk session token |
| AWS Cognito | `X-Cognito-ID-Token` | Raw access or ID token |
| Supabase | `X-Supabase-Access-Token` | Raw access token |
| Custom JWT | `X-Omni-User-Token` | Raw JWT |

```sh
curl https://your-proxy/v1/chat/completions \
  -H "authorization: Bearer omk_gH3k…" \
  -H "x-firebase-id-token: $FIREBASE_ID_TOKEN" \
  -H "content-type: application/json" \
  -d '{"model":"gpt-4o-mini","messages":[{"role":"user","content":"Hello!"}]}'
```

Every verifier header and scheme remains configurable. If you override a user verifier to use a
Bearer-style custom header, set its `scheme` to `bearer`; do not reuse `Authorization`.

## Require keys

```yaml
security:
  requireWriteKey: true
```

`requireWriteKey` defaults to `false`, allowing a staged rollout:

1. Generate keys.
2. Ship clients that send them.
3. Confirm traffic is attributed in **Public API Keys** and **Activity Logs**.
4. Set `requireWriteKey: true`.

A presented publishable key is validated even before it is required. Once the setting is enabled,
requests without one receive an OpenAI-style `401` response with `WWW-Authenticate: Bearer`.

## Restrict what a key can reach

A key may carry its own model allowlist, independent of `routing.allowedModels`:

| `allowedModels` | Meaning |
| --- | --- |
| absent / `null` | No key-specific restriction. |
| `["cheap"]` | Only `cheap`. |
| `[]` | No models; park the key without revoking it. |

A disallowed model is reported as `model_not_found`, just like an unknown model. `/v1/models` is
filtered to match.

## Use key identity in routing

The calling application appears in CEL expressions as `client`:

| Variable | Type | Notes |
| --- | --- | --- |
| `client.id` | string \| null | Publishable-key id. |
| `client.name` | string \| null | Reference name. |

Use `client.id != null` when a rule only needs to know whether a publishable key was presented.

```yaml
providers:
  anthropic:
    type: anthropic
    apiKey: ${ANTHROPIC_API_KEY}
  openai:
    type: openai
    apiKey: ${OPENAI_API_KEY}
routing:
  rules:
    - id: internal-tools
      when: client.name == "admin-dashboard"
      target:
        provider: anthropic
    - id: everyone-else
      when: "true"
      target:
        provider: openai
```

Token budgets remain per user. Publishable keys provide client attribution and model restriction;
they do not replace user authentication.
