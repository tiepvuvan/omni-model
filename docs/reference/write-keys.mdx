---
title: Write keys
description: Identify, restrict and revoke the applications calling your proxy.
---

A write key answers **which application is calling**. That is a different question from the one the
[security verifiers](/security/custom-jwt) answer, which is *who is using that application*.

Both matter. A leaked build of your iOS app still presents perfectly valid Firebase Auth tokens —
every request looks like a real user, because it is one. Revoking the app's write key cuts it off
without invalidating a single user session.

## Sending one

```sh
curl https://your-proxy/v1/chat/completions \
  -H "x-omni-key: omk_gH3k…" \
  -H "authorization: Bearer $USER_TOKEN" \
  -H "content-type: application/json" \
  -d '{"model": "gpt-4o-mini", "messages": [{"role": "user", "content": "Hello!"}]}'
```

The key goes in `x-omni-key`, not `Authorization`. The `jwt`, `firebase-auth` and `supabase`
verifiers already use `Authorization` for the end user's token, and a client needs to send both at
once.

## Storage and revocation

Only a SHA-256 of each key is stored, so a database dump cannot be replayed against your proxy. The
plaintext is returned **once**, when the key is created, and is unrecoverable afterwards — lose it
and you issue a new one.

Revoking sets `disabled_at` rather than deleting the row, so request logs keep pointing at a real
client and past usage stays attributable.

<Note>
  Each replica caches key lookups in memory for a few seconds, because otherwise every `/v1`
  request would cost a database query. A revocation therefore takes effect immediately on the
  instance that performed it and within the cache TTL (10s by default) elsewhere.
</Note>

## Requiring them

```sh
OMNI_SECURITY_JSON='{"requireWriteKey":true,"providers":[…]}'
```

`requireWriteKey` defaults to **false** so that enabling it is a deliberate act — turning it on
rejects every client that is not already sending a key.

A presented key is always validated either way, so attribution and revocation start working as soon
as your clients begin sending keys. But revocation only becomes *binding* once `requireWriteKey` is
true: until then, a revoked client can simply drop the header.

The recommended rollout is therefore: create keys → ship clients that send them → confirm traffic is
attributed → set `requireWriteKey: true`.

## Restricting what a key can reach

A key may carry its own model allowlist, independent of `routing.allowedModels`:

| `allowedModels` | Meaning |
| --- | --- |
| absent / `null` | No restriction. |
| `["cheap"]` | Only `cheap`. |
| `[]` | Nothing — a way to park a key without revoking it. |

A disallowed model is reported as `model_not_found`, exactly as an unknown one would be, so a client
cannot map out which models exist by probing. `/v1/models` is filtered to match, so a client is never
told about a model that would 404 for it.

## Using a key in rules

The calling application appears in routing and rate-limit expressions as `client`:

| Variable | Type | Notes |
| --- | --- | --- |
| `client.id` | string \| null | Write key id. |
| `client.name` | string \| null | Write key name. |
| `client.authenticated` | bool | Whether a valid key was presented. |

```sh
OMNI_ROUTING_JSON='{"rules":[
  {"id":"internal-tools","when":"client.name == \"admin-dashboard\"",
   "target":{"type":"anthropic","apiKey":"${ANTHROPIC_API_KEY}"}},
  {"id":"everyone-else","when":"true","target":{"type":"openai","apiKey":"${OPENAI_API_KEY}"}}
]}'
```

Rate limits accept `key: client`, giving each application its own budget:

```sh
OMNI_RATE_LIMITS_JSON='[
  {"id":"per-client","name":"per-client","key":"client","requests":{"limit":10000,"window":"1h"}}
]'
```

<Warning>
  Give every rate-limit rule a stable `id`. Counters are namespaced by `id`, not by `name`, so a rule
  whose identity is its display name silently resets every counter the first time someone renames it.
</Warning>

When no key is presented, a `client`-keyed rule falls back to the request IP, so the rule still means
something before `requireWriteKey` is on.
