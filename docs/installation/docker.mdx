omni-model ships as a single container image. It is the only supported deployment target: run it
on any platform that runs containers, pointed at a PostgreSQL database.

## Requirements

- A container runtime (Docker, Podman, Kubernetes, ECS, Nomad — anything that runs an OCI image).
- A PostgreSQL 14+ database.
- Two stable random values for dashboard sessions and credential encryption.

## Run it

The fastest local setup is the repository's Compose stack:

```sh
git clone https://github.com/tiepvuvan/omni-model.git
cd omni-model
docker build -t omni-model:local .

printf 'OMNI_ADMIN_SECRET=%s\nOMNI_ENCRYPTION_KEY=%s\n' \
  "$(openssl rand -base64 32)" \
  "$(openssl rand -base64 32)" > examples/.env

docker compose \
  --env-file examples/.env \
  -f examples/docker-compose.dashboard.yml \
  up -d --wait
```

Open [http://localhost:8787/admin](http://localhost:8787/admin), create the first operator, and use
the dashboard to configure user authentication, app verification, routing, rate limits, and
publishable keys.

The container can start before that configuration exists: `/healthz` remains available and
`/v1/*` stays closed with `503 not_configured`.

## Schema migrations

The container migrates its own schema on boot, before it accepts traffic. You can start every
replica at once: the whole migration runs in a single transaction guarded by a Postgres advisory
lock, so exactly one instance applies it and the rest wait, then find it done. A process killed
mid-migration leaves nothing half-applied — the transaction rolls back and the lock releases with
the connection.

Migrations are forward-only and additive, which is what makes rolling deploys safe: an older
replica keeps serving against a newer schema (it logs that the database is ahead and carries on).

omni-model owns every `omni_`-prefixed relation in the database or schema you point it at. Nothing
is schema-qualified, so `search_path` decides where the tables live — give omni-model its own
database or Postgres schema if you need isolation. There is no table-name option.

If the runtime database user cannot run DDL, apply the schema as its own step with a privileged
role and let the server run without one:

```sh
omni-model migrate
```

```sh
OMNI_STORAGE_POSTGRES_MIGRATE=false omni-model
```

`migrate` takes the same advisory lock the server does, so it is safe to run from an init container
on every pod start and safe to run while a server is booting. It prints what it applied and exits.

## Optional first-boot configuration

```sh
OMNI_STORAGE_TYPE=postgres
OMNI_STORAGE_POSTGRES_URL=${DATABASE_URL}
OMNI_SECURITY_JWT_ENABLED=true
OMNI_SECURITY_JWT_SECRET=${OMNI_JWT_SECRET}
OMNI_SECURITY_JWT_ALGORITHMS=["HS256"]
OMNI_TARGET_TYPE=openai
OMNI_TARGET_API_KEY=${OPENAI_API_KEY}
OMNI_RATE_LIMITS_JSON=[{"name":"per-user-daily-tokens","tokens":{"limit":30000,"window":"1d"}}]
```

Most deployments can skip this block and use the dashboard. Environment configuration is useful
when infrastructure automation must seed a fresh database without an operator.

<Note>
  Set `OMNI_SERVER_TRUST_PROXY_HEADERS=true` **only** when the container sits behind a reverse
  proxy or CDN that overwrites `x-forwarded-for`. Otherwise a client can spoof its own IP and,
  with it, its rate-limit key. When it is `false`, the proxy uses the real socket peer instead.
</Note>

## Compose

```yaml
services:
  db:
    image: postgres:17-alpine
    environment:
      POSTGRES_USER: omni
      POSTGRES_PASSWORD: secret
      POSTGRES_DB: omni
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U omni"]
      interval: 5s
      retries: 10
  proxy:
    image: ghcr.io/tiepvuvan/omni-model:latest
    ports: ["8787:8787"]
    depends_on:
      db: { condition: service_healthy }
    environment:
      DATABASE_URL: postgres://omni:secret@db:5432/omni
      OMNI_STORAGE_TYPE: postgres
      OMNI_STORAGE_POSTGRES_URL: ${DATABASE_URL}
      OMNI_SECURITY_JWT_ENABLED: "true"
      OMNI_SECURITY_JWT_SECRET: ${OMNI_JWT_SECRET}
      OMNI_SECURITY_JWT_ALGORITHMS: '["HS256"]'
      OMNI_TARGET_TYPE: openai
      OMNI_TARGET_API_KEY: ${OPENAI_API_KEY}
```

## Custom domain with Caddy

The repository includes a production-shaped Compose stack at
`examples/docker-compose.custom-domain.yml`. Caddy is the only public service: it listens on ports
80 and 443, obtains and renews the TLS certificate automatically, and proxies to omni-model on the
private Compose network.

```sh
cp examples/custom-domain.env.example examples/.env
# Edit examples/.env: set OMNI_DOMAIN and generate the three stable secrets.
docker compose \
  --env-file examples/.env \
  -f examples/docker-compose.custom-domain.yml \
  config
docker compose \
  --env-file examples/.env \
  -f examples/docker-compose.custom-domain.yml \
  up -d
```

Before starting it:

1. Point the domain's public `A` and/or `AAAA` records at the host.
2. Allow inbound TCP 80 and 443, plus UDP 443 for HTTP/3.
3. Keep `OMNI_ADMIN_SECRET`, `OMNI_ENCRYPTION_KEY`, and the named volumes stable.

The stack threads `OMNI_DOMAIN` through Caddy, `OMNI_ADMIN_BASE_URL`,
`OMNI_ADMIN_ALLOWED_ORIGINS`, and the initial `server.customDomain` setting. The value saved in
Settings is intentionally not allowed to rewrite Caddy's files from inside the application. If the
hostname changes later, update `OMNI_DOMAIN`, recreate the Caddy and omni-model containers, then
save the same hostname in Settings.

## Configuration lives in the database

The environment is only a **first-boot seed**. On an empty database, the `OMNI_*` variables above
are stored as revision 1; from then on PostgreSQL is authoritative and changing an environment
variable does nothing until you also change the stored configuration.

Saving a new revision reconfigures every running replica **without a restart** — providers, auth
verifiers, rate limits, routing and CORS all swap live, usually within a second. A request already
in flight, including a streaming response, finishes on the configuration it started with.

A configuration that fails validation is **rejected**: the previous one keeps serving and the
reason appears on `/readyz`. A bad edit cannot take the proxy down.

`storage` is the exception — it is read at boot only. Moving to a different database needs a
restart, since there is nowhere else to read a corrected configuration from.

### Configuration in version control

For a configuration that lives in a repository rather than in a dashboard, keep the JSON document as
a file and let CI apply it:

```sh
omni-model import-config omni.config.json --note "$GITHUB_SHA"
```

It validates the document with the same two-step schema a boot uses — so a broken one fails the
pipeline instead of becoming the active revision — then saves it. Every running replica adopts it
from the database; no restart and no admin session are involved.

### Commands

Every command reads the same `OMNI_STORAGE_*` variables the server does, so they always act on the
database the server is using.

| Command | Purpose |
| --- | --- |
| `omni-model` | Serve the proxy (the image's default). |
| `omni-model migrate` | Apply pending migrations and exit. |
| `omni-model import-config <file>` | Validate and save a configuration as a new revision. |
| `omni-model create-admin --email <e>` | Create an operator account without HTTP. |

In a running container, reach them with `docker exec`:

```sh
docker exec omni-model omni-model migrate
```

<Note>
  Stored revisions keep their `${VAR}` references rather than the resolved values, so your
  credentials stay in the platform secret store and never land in the database or in an audit
  trail. They are resolved from the container's environment each time the configuration is applied
  — which means a referenced variable must exist in every replica.
</Note>

## Credentials managed from the dashboard

`${VAR}` works when you control the environment. For credentials an operator types into the dashboard,
omni-model stores them **encrypted in the database** and configuration refers to them by id:

```json
{
  "routing": {
    "rules": [
      { "id": "default", "when": "true", "target": { "type": "openai", "apiKey": { "$secret": "3f7c…" } } }
    ]
  }
}
```

Set a 32-byte master key to enable this:

```sh
docker run -e OMNI_ENCRYPTION_KEY="$(openssl rand -base64 32)" ... ghcr.io/tiepvuvan/omni-model:latest
```

Values are sealed as a **JWE** (`dir` + `A256GCM`) — a standard format, so a stored value is one
opaque string any JOSE library can read given the key, rather than a layout private to omni-model.
The key never leaves the environment, so a database dump — or a leaked backup — contains ciphertext
and nothing else. A configuration revision holds only the reference, which is what makes revisions
safe to diff, export and roll back.

Rotating a credential is a write plus a reload: the reference keeps its id, so no configuration
needs editing.

<Warning>
  **Back up `OMNI_ENCRYPTION_KEY` separately from the database.** Lose it and every stored secret is
  unrecoverable — that is the point of holding it outside the database. Store it wherever you keep
  your other break-glass credentials, not next to a database backup.
</Warning>

### Rotating the master key

Each sealed value names the key that sealed it, in its JWE `kid` header — so rotation needs no
downtime and no migration pass:

```sh
OMNI_ENCRYPTION_KEY=<the new key>
OMNI_ENCRYPTION_KEY_PREVIOUS=<the old key>   # comma-separated; decrypt-only
```

New writes use the new key and old rows keep working. Re-encrypt the old rows when convenient, then
drop `OMNI_ENCRYPTION_KEY_PREVIOUS`. Removing the old key too early is recoverable: reads fail with a
message naming the missing key id, and putting it back restores access.

If a configuration references a secret and no key is set, the configuration is **rejected** — the
proxy keeps serving its previous one rather than starting with a credential it cannot read.

## Health checks

`GET /healthz` returns `{"status":"ok"}` whenever the process is alive, regardless of
configuration — point your platform's **liveness** probe at it. A misconfigured proxy should be
fixed, not restarted in a loop.

`GET /readyz` reports whether this instance can actually serve `/v1`:

```json
{ "status": "ready", "revision": 12, "error": null }
```

It answers 503 with `"status": "not_configured"` when there is no usable configuration, and
`error` carries the reason. Point your **readiness** probe and load-balancer checks at this one.
Neither endpoint needs authentication; until a configuration exists, `/v1/*` answers 503
`not_configured`.

During a shutdown `/readyz` answers 503 with `"status": "draining"` and how many requests are still
in flight — see below.

## Shutting down without cutting answers off

On `SIGTERM` the container stops accepting new work, waits for what is already running, then exits.
A streamed completion is the case that matters: the handler returned long ago and the answer is
still being written, so a naive shutdown truncates it mid-sentence.

In order:

1. New `/v1` requests are refused with 503 `shutting_down`, and `/readyz` reports `draining`. The
   socket stays open on purpose — closing it would make the readiness probe unreachable, and an
   unreachable probe tells a load balancer nothing.
2. In-flight requests finish, streams included.
3. Buffered request logs are flushed, then the connection pool closes.

The wait is bounded by `OMNI_SHUTDOWN_DRAIN_MS` (default `25000`); past it the remaining connections
are cut and the reason is logged, because one client holding a stream open must not stall a deploy.
Give the platform a grace period longer than the drain:

```sh
docker stop -t 30 omni-model
```

```yaml
spec:
  terminationGracePeriodSeconds: 30
```

A second `SIGTERM` or `SIGINT` exits immediately, so `Ctrl-C` during a long stream is never mistaken
for a hang.

## Scaling out

Run as many replicas as you like against one database. Rate-limit counters are incremented in a
single SQL statement, so limits stay exact no matter how many instances serve a user. If the
database becomes unreachable, rate limiting **fails open**: requests keep flowing rather than the
proxy taking your API down with it.
